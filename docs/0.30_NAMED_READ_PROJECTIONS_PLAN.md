# ModelLang 0.30 named read projections

Status: implementation-ready architecture plan. This is not yet the normative 0.30 specification.

## Outcome

ModelLang 0.30 will make every newly compiled query return one explicit, stable, closed projection rather than the complete source entity. A projection defines disclosure shape only. The query remains the sole owner of authentication, operation authorization, row visibility, ordering, and result bounds.

The release stays within the existing PostgreSQL, TypeScript, HTTP, OpenAPI, UI, semantic-manifest, provenance, and migration architecture. It adds no relationship traversal, pagination, filters, aggregates, field-dependent authorization, MCP surface, or failure-operation behavior.

## Alternatives considered

### A. Inline selected fields on each query

Rejected. Inline selection would be a smaller parser change, but each query would own an anonymous result type. Equivalent shapes would be duplicated across queries, output identity would collapse into query identity, and later HTTP, UI, and agent resource projections would lack a reusable stable contract.

### B. Named reusable projections

Selected. A named projection gives output shape and every output member durable identity independent of the query that authorizes it. Multiple queries may reuse the same shape while retaining different authorization and row policies.

### C. Direct MCP or agent manifests

Rejected for 0.30. MCP schemas describe invocation but do not create field disclosure, row authorization, freshness, or runtime enforcement. Agent projection remains downstream of safe read semantics.

## Surface language

The proposed normative form is:

```modellang
projection RequestSummary @stableId("prj_...") from PurchaseRequest {
  id @stableId("pfd_...");
  amount @stableId("pfd_...");
  status @stableId("pfd_...");
}

query myRequests @stableId("qry_...")(
  caller actor: User
) returns RequestSummary from PurchaseRequest as request {
  authorize true;
  where request.requester == actor;
  orderBy request.id asc;
  limit 100;
}
```

`returns RequestSummary` does not include array syntax because query cardinality is already fixed by the language: every query returns one ordered, bounded array. Actions retain `-> Entity` and continue returning one complete post-effect entity.

Projection fields end in semicolons, matching entity fields. Output aliases are not supported in 0.30. A projection field's output name is the selected source field's current name.

## Identity and namespaces

- A projection is a top-level declaration in the global declaration namespace. Its explicit ID uses `prj_[0-9a-f]{32}` and its semantic ID is `projection:<stable-id>`.
- A projection field is a durable member. Its explicit ID uses `pfd_[0-9a-f]{32}` and its semantic ID is `projectionField:<stable-id>`.
- `assign-ids` assigns IDs to both projection declarations and projection fields and remains idempotent.
- Projection-field identity is independent of source-field identity. Each member also stores the selected source field ID. This supports future traversal and aliases without retrofitting identity later.
- Projection names and projection-field IDs must be globally unique under the same collision rules as existing durable declarations.
- Projection declarations are result shapes only. They are invalid as entity fields, action inputs or outputs, policy parameters, event payloads, consumer payloads, or query inputs.

## Type and disclosure rules

A 0.30 projection:

- names exactly one source entity;
- contains at least one field;
- selects only direct stored fields of that source entity;
- may select scalars, enums, exact money, entity references, generated UUID/DateTime fields, and non-collection snapshot fields whose underlying type is otherwise supported;
- represents an entity reference as its UUID identity, never as an implicit nested object;
- rejects enum sets and every other collection-valued field;
- rejects duplicate source-field selections, duplicate projection-field IDs, unknown fields, and unsupported field kinds;
- does not automatically include the source identity field or any other field.

The compiler must require `query.sourceEntityId == projection.sourceEntityId`. A query over `PurchaseRequest` cannot return a projection declared from `User`, even when field names happen to overlap.

Projection selection is an allowlist. Query predicates and ordering may reference direct fields that are not selected. Such fields remain enforcement inputs and never appear in output.

Selected optional fields are required JSON object keys whose value is `null` when the stored value is null. Omission is invalid. This rule applies identically to PostgreSQL JSONB, TypeScript, JSON Schema, OpenAPI, HTTP validation, and UI metadata.

Projection member order is not part of the JSON or semantic compatibility contract. Generators may preserve declaration order for readability, but consumers must not infer meaning from it.

## Authority boundary

```text
authenticated principal
        |
        v
query authorization  ---- fail ----> authorization error
        |
        v
row policy over source rows
        |
        v
bounded deterministic ordering
        |
        v
projection allowlist
        |
        v
closed JSONB array
```

The projection contributes no authorization expression, caller binding, row filter, capability, or visibility grant. Reusing one projection from two queries does not couple their authority. PostgreSQL continues to resolve caller identity and enforce each query independently before constructing projected JSON.

No projection can address private runtime tables or columns because resolution begins from declared entity fields in canonical IR. Generated SQL must build selected keys directly and must never construct a complete entity object followed by deletion or redaction.

## Canonical IR19

IR19 adds:

```ts
interface IRProjectionField {
  id: string;
  name: string;
  identity: IRIdentity;
  sourceFieldId: string;
  span: IRSpan;
}

interface IRProjection {
  id: string;
  name: string;
  identity: IRIdentity;
  sourceEntityId: string;
  fields: IRProjectionField[];
  span: IRSpan;
  naming: { typescriptName: string };
}
```

`ModelIR` gains `projections: IRProjection[]`. `IRQuery` replaces its implicit source-entity result with `returnProjectionId` while retaining `sourceEntityId` for row evaluation.

The IR stores source-field IDs rather than copied type definitions. Generators resolve type, nullability, generation, immutability, storage, and target naming from the canonical source entity. This avoids two independently mutable type descriptions.

Current 0.30 source always emits explicit projection output. An internal evolution-only discriminator represents released IR9 through IR18 queries whose output was an implicit full entity. That compatibility representation is accepted only while reading a released baseline and is never emitted by the current compiler.

## Public and engineering contracts

### Operation manifest v5

Operation manifest v5 adds closed projection definitions reachable from declared queries:

```json
{
  "projections": [
    {
      "id": "projection:prj_...",
      "name": "RequestSummary",
      "sourceEntityId": "entity:ent_...",
      "fields": [
        {
          "id": "projectionField:pfd_...",
          "sourceFieldId": "field:fld_...",
          "name": "amount",
          "type": { "kind": "money", "currency": "USD", "precision": 19, "scale": 2 },
          "nullable": false
        }
      ]
    }
  ]
}
```

Action output remains `{ entityId, cardinality: "one" }`. Query output becomes `{ projectionId, cardinality: "many", maxItems }`. Only projections reachable from queries appear in the public operation manifest. Unused declarations remain in canonical IR and the engineering semantic manifest but do not widen the public contract.

### UI manifest v5

UI manifest v5 adds projection descriptors derived from operation manifest v5. Each query uses `resultProjectionId` instead of `resultEntityId`. Query result columns come only from that projection. Entity descriptors remain available for action results and entity-reference inputs; their presence grants no data access.

### OpenAPI and HTTP

- OpenAPI defines one closed component schema per reachable projection.
- Every selected property is required; optional source fields use nullable value schemas.
- Query responses reference the projection component, never the source-entity component.
- The generated HTTP server validates query results with `validProjection` and continues validating action results with `validEntity`.
- Missing, extra, incorrectly typed, or incorrectly nullable projection keys fail server-side output validation.
- Stable query routes remain unchanged because they continue to derive from the query ID.

### TypeScript

- Generate one exported interface per reachable projection.
- PostgreSQL, gateway, HTTP, browser, and UI query methods return `Promise<ProjectionName[]>`.
- Action and event payload interfaces remain complete entity types.
- UI operation-ID result maps use projection array types for queries and entity types for actions.

### Semantic manifest v11

Semantic manifest v11 records every declared projection, its source entity, ordered members, member IDs, selected source-field IDs, and source spans. Each query records `output.projectionId` and a separate disclosure set. Existing authorization and row-policy read sets remain unchanged so enforcement dependencies cannot be confused with disclosed fields.

### Other versions

- canonical IR: 19;
- operation manifest: 5;
- capability manifest: 4, because it names operation manifest v5 even though its action-only shape remains otherwise unchanged;
- UI manifest: 5;
- engineering semantic manifest/profile: 11;

## PostgreSQL generation

Query functions continue returning JSONB. No PostgreSQL composite type is introduced.

The query subselect keeps the current authorization, source scan, `WHERE ... IS TRUE`, deterministic ordering, primary-key tie breaker, and fixed limit. Its item expression changes from complete `rowJson(sourceEntity, v_row)` to `projectionJson(projection, v_row)`.

`projectionJson` resolves every member to a declared source column and calls `jsonb_build_object` only with selected keys. It reuses the current decimal, exact-money, DateTime, enum, UUID, optional, and entity-reference encodings. The result remains one JSONB array and uses the same statement-level MVCC snapshot.

## Evolution and compatibility

Evolution compares declarations by stable ID and projection members by projection-field ID.

| Change | Classification | Safe migration |
|---|---|---|
| Add unused projection | additive | allowed |
| Add query with a new or existing projection | additive | allowed |
| Rename projection with stable ID | identity-preserving additive | allowed; generated source name changes |
| Reorder projection fields | no semantic change | allowed |
| Add member to an existing reachable projection | breaking | rejected; closed output gains a required key |
| Remove member from an existing reachable projection | breaking | rejected |
| Rename a selected source field | breaking for every projection that exposes it | rejected; the JSON key changes because aliases are absent |
| Change selected source field for an existing member ID | breaking | rejected |
| Change selected field type or nullability | breaking | rejected |
| Change projection source entity | breaking | rejected |
| Change an existing query's return projection | breaking | rejected |
| Remove projection | breaking | rejected unless unreachable and explicitly reviewed |

Released IR9 through IR18 baselines normalize their query result as `legacyEntity`. Comparing `legacyEntity` with an explicit 0.30 projection produces one breaking query-output change plus the exact disclosed-field delta. The automatic safe planner rejects that change. The reviewed planner may redeploy the query after an acknowledgement tied to the stable query and projection IDs.

This means upgrading either canonical 0.29 example to its intentionally narrowed 0.30 query requires a reviewed migration. Fresh 0.30 installations need no compatibility shim. No historical projection identity or read evidence is fabricated.

Projection changes do not require table DDL. Accepted migrations transactionally replace query functions, grants, and migration history through the existing model migration path. Manifests and clients are regenerated as deterministic build artifacts outside the database transaction. The private PostgreSQL runtime profile stays at 29 because 0.30 changes no private failure-operation subsystem.

## What already exists

- The parser already treats language keywords contextually, so `projection`, `from`, and `returns` require no reserved-word system.
- Stable declaration IDs, collision checking, assignment, rename comparison, and source spans provide the identity framework to extend.
- `IRQuery.sourceEntityId`, authorization, row policy, ordering, and limit already describe the full enforcement boundary and remain authoritative.
- `rowJson` already implements canonical entity-field JSON encoding. Projection generation should extract and reuse a field-value encoder instead of duplicating money and nullable rules.
- Operation manifest already drives OpenAPI, HTTP, browser, and UI generation. Projection output must enter at this shared contract rather than being reinterpreted separately by each target.
- `validateOutput` already enforces closed output objects and maximum result counts. It should gain a projection branch, not a second validator stack.
- Semantic diff and the safe/reviewed planners already separate analysis from migration authority.
- Golden fixtures, schema validation, deterministic provenance, and live PostgreSQL tests already provide release gates.

## Implementation sequence

### 1. Language and canonical boundary

Update syntax AST, parser, resolver, stable-ID assignment, type checking, IR types, IR schema, validation, version constants, and compiler tests. Establish projection/source compatibility and field-kind diagnostics before changing any generator.

### 2. Shared contract manifests

Advance and update operation, UI, capability, semantic, semantic-diff, and provenance contracts plus their JSON Schemas. Add projection lookup helpers shared by generators. Extend Mermaid and enforcement artifacts so a query's source read and disclosed projection remain distinguishable. Keep decision and event manifests unchanged except where their IR-version schema constant must advance.

### 3. Runtime and client generation

Refactor PostgreSQL field JSON encoding, generate selected JSONB keys, and update TypeScript database, gateway, HTTP, browser, and UI result typing and runtime validation. Preserve action and event entity outputs.

### 4. Evolution

Add released-baseline normalization, projection diffs, safe-planner rejection, reviewed acknowledgements, and transactional query redeployment coverage. Do not add a private operational upgrade.

### 5. Canonical models and release documentation

Add `RequestSummary` and `ReservationSummary` projections, update both queries, advance model versions, write the full `spec/0.30/` set, update README, SPEC, CHANGELOG, and the whitepaper implementation status, then regenerate every golden artifact.

### 6. Verification

Run the complete health, model validation, deterministic generation, demos, migration, privacy, path, and diff checks. Delete `NEXT_SESSION.txt` only after implementation, documentation, regeneration, and release verification are complete.

## Failure modes and required defenses

| Failure | User-visible impact | Defense |
|---|---|---|
| SQL constructs a full row before redaction | Unselected data may cross the database boundary | SQL-text assertion and live exact-key test |
| Query and projection source entities differ | Wrong columns, invalid SQL, or accidental disclosure | Compile-time source-ID equality diagnostic |
| HTTP still validates the source entity | Every valid projected response becomes a server 500 | Cross-artifact output test through generated handler |
| Optional fields are omitted instead of null | OpenAPI, TypeScript, and runtime disagree | Required-key nullable contract and live null test |
| Projection reuse imports authority | One query can expose another query's rows | Projection has no rules; integration test with two policies |
| Legacy output narrowing is called safe | Existing strict consumers break without review | Breaking semantic diff and safe-planner rejection |
| Manifest includes unused projections | Public metadata surface grows without a callable query | Reachability filtering in operation/UI/OpenAPI artifacts |
| Projection member encoding drifts from entity encoding | Money, Decimal, or references change representation | One shared field-value encoder and parity tests |
| Mermaid or enforcement output still implies whole-entity disclosure | Reviewers receive a false account of the read boundary | Golden assertions for source reads and projection output edges |

No failure mode is intentionally silent. Compile-time model errors, schema validation, generated server validation, migration refusal, or live database tests cover each boundary.

## Performance

The database scan, predicate, sort, tie breaker, limit, and MVCC behavior remain unchanged. Constructing fewer JSON keys reduces result bytes and normally reduces JSON construction work. The implementation must not introduce per-row subqueries, relationship loads, or post-query JavaScript redaction.

Compiler projection resolution should use maps keyed by projection and field ID. No caching layer or new runtime service is warranted.

## NOT in scope

- Output aliases: deferred until their evolution and collision rules can be specified without weakening member identity.
- Relationship traversal or nested objects: 0.31 will define bounded to-one traversal and dependency closure.
- Collection-valued projection fields: excluded with all other collection traversal in 0.30.
- Cursor or offset pagination: fixed bounded queries remain unchanged.
- Optional filters, authored sort profiles, aggregates, grouping, and computed fields: later read-family releases.
- Conditional field visibility or redaction: 0.35 will distinguish field disclosure from row authorization.
- Read evidence, audit, freshness, or as-of semantics: 0.36.
- Target capability profiles and extension ledger: 0.37.
- MCP, agent views, or task packets: 0.38 and later.
- Private failure observation, acknowledgement, claiming, recovery, or runtime-profile changes: unrelated to semantic reads.
- Cross-model reads and context federation: outside the 0.30 family.

## Parallelization

The language/IR step is a hard dependency. After IR19 is stable, contract-manifest work and PostgreSQL/TypeScript runtime work can proceed in parallel, but both converge on HTTP/UI generation and golden fixtures.

```text
Lane A: language + IR19
             |
             +--> Lane B: manifests + schemas + semantic diff --+
             |                                                   |
             `--> Lane C: PostgreSQL + TypeScript generators ----+--> integration + docs + goldens
```

Because generated fixtures and version constants are shared, final integration must be sequential. If implemented by one agent, follow the numbered sequence and avoid parallel worktrees.

## Completion gate

Implementation is complete only when:

1. both canonical models use explicit projections;
2. no current query can compile without one;
3. every public query artifact references projection identity rather than source-entity output identity;
4. PostgreSQL returns only selected keys under live authorization and privilege tests;
5. legacy evolution is honestly classified and reviewed;
6. all changed schemas and golden artifacts are deterministic;
7. the full verification commands in `NEXT_SESSION.txt` pass; and
8. documentation makes clear that projections define shape, never authority.
