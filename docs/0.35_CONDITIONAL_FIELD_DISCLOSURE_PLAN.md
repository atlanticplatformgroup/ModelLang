# ModelLang 0.35 conditional field disclosure plan

Status: implemented in the 0.35 reference compiler.

## Goal

Allow a model author to keep a stable projection shape while revealing selected values only under explicit row-aware conditions. The feature must fail closed, retain static SQL and closed output schemas, and remain strictly weaker than query authorization and row visibility.

## Contract

Projection members opt into a nullable contract with `redactable` after their stable ID. Queries declare up to 32 `disclose path when Boolean;` rules between `where` and `orderBy`. Paths follow only explicit nested projection members, rules are query-local, and every redactable ancestor on a nested path needs an independent rule.

The JSON key is always present. A true rule yields the projected value; false, unknown, or no rule yields `null`. Redaction does not omit keys, emit sentinel strings, add rows, widen authorization, or grant access to fields outside the projection.

## Execution and artifacts

IR24 records projection redaction eligibility plus stable query-scoped rule identity, output path, typed condition, source text, and span. PostgreSQL emits only static `CASE WHEN (...) IS TRUE` branches. TypeScript, operation/OpenAPI/HTTP, UI, semantic, enforcement, provenance, and schemas derive the same required-key/nullable-value contract and fail-closed metadata.

Disclosure conditions use the existing query scope and may depend on the source row, caller, declared inputs, literals, enum members, and reusable policies. No new runtime callable input or dynamic projection mechanism is introduced.

## Evolution and verification

Projection redaction eligibility changes are breaking. Rule additions are expansive, removals restrictive, and condition changes use Boolean semantic classification where provable or require review. Paginated query revisions include disclosure rules.

Verification covers parser/type diagnostics, nested-path constraints, IR and enforcement evidence, static SQL, nullable generated types, exact HTTP validation, operation/UI/semantic metadata, semantic evolution, deterministic golden artifacts, and live PostgreSQL behavior before and after the Procurement request leaves draft state.
