# ModelLang 0.49.1 to 0.50 pilot roadmap

Status: completed 8 August 2026. This historical roadmap records how the ToolShare public-preview pilot findings became the 0.49.1 patch and 0.50 release. The implementation language and acceptance criteria below are intentionally retained in their original planning tense. Later expressiveness work should be justified by domains that remain awkward after transactional composition is available.

## 0.49 patch release before public launch

The patch release must not change the language, canonical IR, generated authority model, MCP contracts, or compatibility claims. It should repair the compiler defect and close the most important developer-experience gaps discovered by the external ToolShare pilot.

### Fix nested-projection `assign-ids` emission

`modelc assign-ids` currently emits a nested projection field in the wrong syntactic order:

```modellang
a @stableId("pfd_..."): ASummary;
```

The compiler accepts the annotation after the projection type:

```modellang
a: ASummary @stableId("pfd_...");
```

Required work:

- correct the stable-ID rewriter for nested projection fields;
- verify that rewriting produces source accepted by the current parser;
- ensure a second `assign-ids` run is idempotent;
- confirm that scalar projection fields and all other stable-ID locations remain unchanged;
- improve the failure path if generated source ever fails its own parser.

Acceptance criteria:

- the ToolShare minimal reproduction rewrites and checks successfully;
- the assigned nested-field ID is preserved through compilation into IR1;
- repeated assignment produces no additional source changes;
- the complete existing stable-ID suite remains green.

### Add the regression test

Use the pilot's minimal reproduction directly:

```modellang
entity A { id: UUID @id; }
entity B { id: UUID @id; a: A; }
projection ASummary from A { id; }
projection BSummary from B { a: ASummary; }
```

The regression should execute the same public behavior as a developer: write the model, run `assign-ids`, parse or check the rewritten model, inspect the nested projection field, and run `assign-ids` again to prove idempotence. A source-only unit test may supplement this test but must not replace the CLI-level proof.

### Add a runnable host/bootstrap guide

The public-preview documentation currently explains generated artifacts and host responsibilities but does not take a developer from generation to a running authenticated application. Add a copyable, minimal host recipe that covers:

1. applying generated PostgreSQL files in their required order;
2. creating a least-privilege gateway login;
3. seeding model principals and `gateway_principal_binding` records;
4. verifying issuer, audience, subject, expiry, and other authentication claims at the host boundary;
5. binding verified issuer and subject values transaction-locally through the generated gateway executor;
6. adapting Node HTTP requests and responses to the generated Fetch-style HTTP handler;
7. constructing MCP authentication context from the same verified identity;
8. mounting the generated MCP adapter without creating connection-scoped authority;
9. shutting down HTTP, MCP, and PostgreSQL resources cleanly; and
10. exercising one allowed and one denied operation through both HTTP and MCP.

The guide must clearly distinguish demonstration authentication from production identity verification. It must not encourage callers to send principal IDs as ordinary action inputs or imply that discovery metadata grants authority.

Acceptance criteria:

- a clean consumer can follow the guide without reading generated implementation code;
- the example runs using only the installed package, generated application, PostgreSQL, and host-owned bootstrap code;
- HTTP and MCP share the same verified subject mapping and runtime policy boundary;
- reconnecting as another subject does not retain prior authority;
- all schema and module lookups resolve through the installed package rather than a ModelLang checkout.

### Reduce harmless PostgreSQL `REVOKE` warning noise

Fresh database initialization currently emits expected warnings when generated SQL revokes privileges that have not previously been granted. The warnings make a successful first run look unhealthy.

Required work:

- identify every expected warning and the generated statement responsible for it;
- suppress or avoid only warnings that are proven harmless and deterministic;
- preserve deny-by-default privileges and idempotent migration behavior;
- do not hide unexpected PostgreSQL warnings or errors globally.

Acceptance criteria:

- clean initialization no longer prints the known harmless warning wall;
- privilege tests prove that application and gateway roles retain exactly the intended access;
- repeated initialization or migration remains safe;
- unexpected database failures remain visible and fail the command.

### Patch release gate

Before the patch is released:

- rerun the ToolShare reproduction against the packed tarball;
- run deterministic model generation checks;
- run the real-tarball package proof under Node.js 20 and the current development Node.js line;
- run the complete health suite, including live PostgreSQL integration;
- confirm the patch contains no semantic IR or generated-contract version changes;
- update the changelog and public-preview documentation;
- publish only after the public repository, package ownership, and trusted-publishing configuration are ready.

## Next language milestone: atomic multi-entity effects

The first semantic milestone after the patch should address application composition. A domain action must be able to perform multiple related effects atomically. In ToolShare, approving a reservation should transition the reservation and create its loan in one transaction.

### Desired semantic model

An action may declare an ordered set of effects over explicitly bound entities. The complete action either commits every effect or commits none. Every effect remains subject to generated authorization, row policy, preconditions, workflow rules, concurrency checks, audit evidence, and private disclosure constraints.

The design must define:

- how create, update, transition, and delete effects compose;
- whether a newly created record can be referenced by later effects;
- deterministic effect ordering and dependency validation;
- authorization timing for every affected record;
- precondition evaluation against the transaction's initial state versus earlier effects;
- optimistic concurrency behavior for multiple existing records;
- database locking order and deadlock avoidance;
- rollback behavior for policy, constraint, and persistence failures;
- stable action inputs and outputs when multiple records change;
- generated HTTP and MCP response envelopes;
- audit, provenance, private read evidence, and decision evidence per effect;
- retry and idempotency expectations; and
- semantic-diff and migration consequences.

### IR version decision

Do not force this feature into IR1 merely to avoid a version change. First determine whether IR1 can represent ordered multi-entity effects without changing the meaning of existing fields or weakening validation. If the canonical IR schema needs new semantic structures, advance the current canonical IR deliberately and update the compiler, schemas, specification, generators, golden artifacts, semantic diff, and conformance tests together.

Historical compatibility should not be added automatically. ModelLang should continue accepting only its current canonical IR unless a real consumer requirement justifies compatibility machinery.

### Minimum proving scenario

The milestone is not complete until an external model can express and prove this transaction:

1. a staff subject approves a pending reservation;
2. the reservation transitions to `APPROVED`;
3. a related loan is created with the approved time window;
4. overlapping approved loans are rejected by PostgreSQL;
5. any failure rolls back both the transition and creation;
6. a concurrent or repeated approval cannot create a second loan;
7. HTTP and MCP expose the same result and denial behavior; and
8. evidence identifies the action and every affected record without disclosing private data.

## Subsequent expressiveness

These capabilities should follow transactional composition rather than being bundled into it. Re-run ToolShare and at least one unrelated domain after multi-entity effects land, then implement only the remaining justified gaps.

### Relational existence and absence predicates

Allow bounded queries such as "reservations with no related loan" and "equipment with an active inspection" without loading broad record sets into host code.

The design must specify relationship direction, cardinality, subject-visible rows, policy interaction, SQL generation, pagination stability, and whether predicates test the existence of an authorized row or an underlying private row. Private-row existence must not become a disclosure channel.

### Bounded relationship traversal in action conditions

Consider safe, statically bounded traversal such as testing an explicitly related equipment record from a reservation condition. Avoid arbitrary graph traversal.

Any design must preserve explicit authorization and predictable locking. The compiler should make it clear which related records are read, which policies apply, what evidence is emitted, and whether the read participates in concurrency validation.

### Conditional temporal constraints

Evaluate whether domains still need conditions such as applying `noOverlap` only when a record is `APPROVED` after multi-entity effects allow approved windows to live in dedicated records.

If retained, conditions must compile to race-safe PostgreSQL enforcement rather than read-before-write application checks. Define supported predicates, nullability, migration behavior, database-index strategy, and diagnostic behavior for unsupported conditions.

### More specific HTTP error classification

Refine the mapping from generated runtime failures to HTTP status codes. In particular, distinguish state or uniqueness conflicts from failed action preconditions where doing so is stable and useful.

The change must preserve machine-readable error identities across HTTP and MCP. Status refinements must not disclose whether a private record exists, reveal hidden policy facts, or make clients depend on database-specific error text.

## Sequencing principle

Fix correctness and public onboarding before adding language surface. Then implement atomic composition as a focused semantic milestone. Only after testing that capability in external applications should ModelLang expand relational queries, traversal, temporal constraints, or transport error taxonomy.
