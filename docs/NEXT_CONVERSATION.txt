Semantics that must remain locked:

- Entity equality means primary-key identity equality.
- caller actor comes only from authenticated context and is never caller-supplied input.
- @snapshot is explicitly assigned stored point-in-time data.
- Money is exact and currency-typed.
- Generated UUID/timestamp fields are database-owned.
- Durable declarations have stable semantic IDs.
- Workflows bind legal state transitions to actions.
- PostgreSQL is the first enforcement backend; canonical IR remains the backend boundary.
- Discovery, applicability, and execution are separate concepts.
- Applicability is a pure authenticated query over current authoritative state.
- authorize failure is denied; require failure is notApplicable.
- Missing and invisible entity references share the authorization-denial projection by default.
- Public explanations are safe projections keyed only by allowlisted stable rule IDs.
- Applicability and execution consume one canonical generated decision plan.
- Execution locks, reloads, and re-evaluates the plan inside the mutation transaction.
- Applicability success and opaque revisions grant no authority.
- stale is possible only when an explicit expected revision is compared.
- The public capability manifest is filtered and must never expose compiler engineering semantics, expressions, current values, SQL details, or full decision traces.

Recommended next milestone: ModelLang 0.18 — reusable policies and durable decision evidence
-------------------------------------------------------------------------------------------

Goal: close the gap between a safe applicability answer and precise, auditable evidence of which declared authority justified an executed action. Do not start MCP/agent generation yet.

Proposed scope:

1. Add first-class, stable-ID reusable policy declarations to .model.
2. Allow authorize and require rules to invoke typed policies without adding imperative callbacks or backend-specific syntax.
3. Extend the canonical decision representation so policy identity, composition, and result branches are shared by applicability and execution.
4. Record durable execution decision evidence transactionally with action audit: action ID, model/source identity, stable policy/rule IDs, outcome, and the exact authority used.
5. Keep public applicability explanations filtered and allowlisted. Do not expose evaluated facts, arbitrary reason strings, internal expressions, or full traces.
6. Update Procurement so approval evidence distinguishes MANAGER authority from FINANCE authority instead of treating the caller's complete role snapshot as the exact decision basis.
7. Generate policy-to-enforcement and policy-coverage reporting.
8. Add compiler, schema, golden, transport, migration, and live PostgreSQL tests proving policy reuse, deterministic evidence, applicability/execution agreement, transaction rollback, and exact approval authority.

Architectural decisions to specify before implementation:

- Policy declaration and invocation syntax.
- Whether policy v1 is Boolean-only or returns a closed structured decision; prefer the smallest type-safe design that can represent exact authority without arbitrary payloads.
- Stable identity, parameter typing, scoping, composition, evaluation order, null/fail-closed behavior, and prohibition of recursion and side effects.
- How an authorization expression identifies one exact successful authority when multiple branches could pass.
- Which evidence is durable, which is public, and which remains internal; include confidentiality and retention implications.
- How action_audit evolves without breaking existing installations, safe migrations, reviewed migrations, or the 0.17 upgrade path.
- Whether canonical IR must advance from IR9. Do not advance it unless the source semantics cannot be represented compatibly.
- Whether operation manifest v2, UI manifest v2, capability manifest v1, and HTTP routes can remain unchanged. Prefer preserving them unless the public contract genuinely changes.
- How policy renames and semantic changes participate in stable-ID diffing and both guarded migration authorities.

Implementation constraints:

- Preserve every 0.17 semantic and security boundary.
- Keep PostgreSQL concepts out of browser/public contracts.
- Do not let audit evidence, applicability results, revisions, or policy IDs become capability tokens.
- Do not infer exact authority from expression text at runtime. Make it explicit and typed in the semantic representation.
- Fail closed for unsupported policy constructs and ambiguous evidence.
- Update normative spec, schemas, README, changelog, repository whitepaper, generated golden artifacts, and version metadata together.
- Run npm run build, npm run model:check, npm test, npm run demo, and npm run demo:reservations before release.
- Commit the finished milestone on main using the historical release style, for example:
  feat: release ModelLang 0.18 policy decisions

Start by reviewing the 0.18 proposal against the whitepaper and existing 0.17 decision-plan boundary. Lock the architectural decisions above, then implement only once the scope is coherent.
