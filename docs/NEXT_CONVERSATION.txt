Released 0.19 architecture
--------------------------

- Canonical IR11 adds explicit per-action reliability semantics while preserving IR10 reusable-policy semantics.
- `idempotency required;` is action-local and requires an execution key. Unmarked actions reject a supplied key.
- Private command identity is authenticated principal plus stable action ID plus key. Identity is never caller input.
- The SHA-256 request fingerprint covers stable action ID, canonical typed callable arguments keyed by stable parameter ID, expected revision, correlation ID, and causation ID. Model source hash is checked separately.
- A command receipt is claimed inside the mutation transaction. Effect, action audit, exact decision evidence, receipt completion, and stored result commit or roll back together.
- Equivalent concurrent retries serialize and replay the one committed stored result. Failed execution leaves no receipt. Changed input or source fails with `ML_IDEMPOTENCY_CONFLICT` without disclosing the result.
- Committed replay does not re-authorize or recheck mutable state because it performs no new effect.
- Idempotency keys, fingerprints, receipts, and stored responses remain private. Public manifests expose only static reliability requirements.
- Correlation and causation are execution metadata, not model inputs or capabilities. Reliable correlation defaults to the key; other actions receive a boundary-generated UUID (inside PostgreSQL for direct execution and at HTTP for response echoing).
- Applicability rejects command metadata, creates no receipt, remains authenticated and side-effect free, and grants no execution authority.
- Operation manifest v3, capability manifest v2, UI manifest v3, semantic manifest v3, and semantic diff v4 carry the new static reliability contract. Decision plan v2 and stable HTTP operation routes remain unchanged.
- IR9 and IR10 remain accepted released evolution baselines when current source compiles to IR11. Idempotency changes fail safe migration and require reviewed acknowledgement.
- `009_upgrade_0_19.sql` is the baseline-checked idempotent receipt/correlation-boundary upgrade. Receipt retention is deployment-governed; generated runtime code never deletes receipts automatically.

Semantics that remain locked
----------------------------

- Policy v1 is pure Boolean and closed; exactly one stable `allow` branch grants authority.
- Decision plan v2 is the one internal expression-bearing input to applicability and execution.
- Entity equality is primary-key identity equality.
- Caller identity comes only from authenticated context and is never caller input.
- `@snapshot` is explicitly assigned stored point-in-time data.
- Money is exact and currency-typed; command fingerprints canonicalize Money to its declared scale and Decimal with `trim_scale`.
- Generated UUID/timestamp fields are database-owned.
- Durable declarations have stable semantic IDs.
- Workflows bind legal state transitions to actions.
- PostgreSQL is the first enforcement backend; canonical IR is the backend boundary.
- Discovery, applicability, execution, and committed replay are separate.
- `authorize` failure is denied; `require` failure is notApplicable.
- Missing and invisible entity references share authorization denial by default.
- Public explanations contain only allowlisted stable action-rule IDs.
- New execution locks, reloads, and re-evaluates the canonical plan inside the mutation transaction.
- Applicability, opaque revisions, policy IDs, authority IDs, audit evidence, and receipts grant no authority.
- `stale` requires an explicit expected revision comparison.
- Generated artifacts are committed golden fixtures and remain byte-for-byte synchronized.

Verification contract
---------------------

Before the next release run:

- npm run build
- npm run model:check
- npm test
- npm run demo
- npm run demo:reservations
- git diff --check

Do not expose `decisions.json`, private decision evidence, command receipts, idempotency keys, request fingerprints, or stored responses to MCP/agent consumers. Any future agent-facing contract must be a separately filtered, authorization-aware projection.
